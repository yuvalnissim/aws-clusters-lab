# Manual Setup and Rebuild Notes

This document records the manual steps used in this lab.
The repository is not yet a fully automated, one-command rebuild.

## 1. Local prerequisites

Install Git, AWS CLI, Terraform, kubectl, and an editor.

The Terraform provider currently uses:

- AWS profile: aws-lab
- AWS Region: eu-north-1

Authenticate before running Terraform:

```powershell
aws login --profile aws-lab --region eu-north-1
aws sts get-caller-identity --profile aws-lab
```

Review the provider configuration if using a different account,
profile, or Region.

Initialize, review, and apply infrastructure:

```powershell
terraform init
terraform validate
terraform plan "-out=rebuild.tfplan"
terraform apply "rebuild.tfplan"
```

Review costs and the complete plan before applying.
The configuration creates both clusters and their worker nodes.

Keep Terraform state outside Git. Preserve the existing state when
managing an existing deployment.

## 2. Prepare the private runner

Connect to the runner EC2 instance using SSM Session Manager.

The instance must have outbound connectivity and its SSM IAM policy.

Install the required tools on the instance:

- Git
- AWS CLI
- Terraform
- kubectl compatible with the clusters
- Helm

For Amazon Linux 2023, the packages used during setup included:

```bash
sudo dnf install -y git unzip libicu
```

Terraform, kubectl, and Helm were downloaded from their official
release sources, checked against published SHA-256 checksums,
and installed under /usr/local/bin.

Recorded versions:

- Terraform: 1.16.6
- kubectl: 1.37.1
- Helm: 4.3.1
- GitHub Actions runner: 2.338.2

Use supported versions and verify download checksums when rebuilding.

## 3. Register the GitHub Actions runner

In the repository, open:

Settings → Actions → Runners → New self-hosted runner → Linux → x64.

Use the download and registration instructions generated by GitHub.
Do not store registration tokens in this repository.

Registration settings:

- Group: Default
- Name: aws-lab-runner
- Additional label: aws-lab
- Work folder: _work

Install and start the runner service from its installation directory:

```bash
sudo ./svc.sh install ssm-user
sudo ./svc.sh start
sudo ./svc.sh status
```

Confirm that GitHub displays the runner as Idle.

## 4. Configure kubectl on the runner

The runner uses its EC2 IAM role. No static AWS keys are required.

```bash
aws eks update-kubeconfig \
  --name aws-clusters-lab-internal \
  --region eu-north-1 \
  --alias lab-internal

aws eks update-kubeconfig \
  --name aws-clusters-lab-public \
  --region eu-north-1 \
  --alias lab-public
```

Use an explicit context with kubectl and Helm commands.

The application deployment workflows create their own temporary
kubeconfig files.

## 5. Temporary controller installation permissions

Normal runner permissions allow viewing cluster resources and
editing application resources in the default namespace.

Installing the Load Balancer Controller also requires cluster-level
permissions.

For this lab, a temporary Terraform configuration granted the runner
AmazonEKSClusterAdminPolicy separately in each cluster.

To reproduce that bootstrap step, create bootstrap-install.tf:

```hcl
resource "aws_eks_access_policy_association" "controller_install" {
  for_each = {
    internal = aws_eks_cluster.internal.name
    public   = aws_eks_cluster.public.name
  }

  cluster_name  = each.value
  principal_arn = aws_iam_role.runner.arn
  policy_arn    = "arn:aws:eks::aws:cluster-access-policy/AmazonEKSClusterAdminPolicy"

  access_scope {
    type = "cluster"
  }

  depends_on = [
    aws_eks_access_entry.runner_internal,
    aws_eks_access_entry.runner_public,
  ]
}
```

Review and apply the temporary grants from the local workstation.

These grants do not expire automatically. Remove them after
controller installation by removing the temporary .tf file from
the active configuration, reviewing the plan, and applying only
the intended access-policy removals.

Do not commit active temporary administrator grants.

## 6. Install AWS Load Balancer Controller

Terraform creates the Pod Identity Agent, dedicated controller roles,
IAM policy attachments, and Pod Identity Associations.

Install the controller from the runner:

```bash
helm repo add eks https://aws.github.io/eks-charts
helm repo update eks
```

Obtain the current VPC ID from `terraform output vpc_id` on the local
workstation, and set it on the runner:

```bash
export LAB_VPC_ID="REPLACE_WITH_CURRENT_VPC_ID"
```

Install in both clusters:

```bash
for environment in internal public; do
  helm upgrade --install aws-load-balancer-controller \
    eks/aws-load-balancer-controller \
    --version 3.6.2 \
    --kube-context "lab-$environment" \
    --namespace kube-system \
    --set "clusterName=aws-clusters-lab-$environment" \
    --set region=eu-north-1 \
    --set "vpcId=$LAB_VPC_ID" \
    --set serviceAccount.create=true \
    --set serviceAccount.name=aws-load-balancer-controller \
    --set replicaCount=2 \
    --wait \
    --timeout 5m || break
done
```

The chart version must match the controller IAM policy version
stored under policies/.

Verify both controller Deployments report READY 2/2.

Remove the temporary administrator grants. Then confirm in each
context that creating ClusterRoles is denied and creating Ingresses
in default is allowed.

## 7. Update environment-specific references

A rebuild creates new AWS resource IDs and ALB DNS names.

Before deploying the internal application:

1. Read `terraform output internal_alb_security_group_id`.
2. Update the security-groups annotation in k8s/internal/demo.yml.
3. Commit and push that change.

Do not reuse an old Security Group ID after destroying the environment.

The Helm commands also require the current VPC ID.

## 8. Deploy and validate applications

Run the GitHub Actions workflows manually on main:

- Deploy internal demo
- Deploy public demo

Wait for the Ingress addresses and ALB target health checks.

Verify:

- Both applications have two Ready replicas on different nodes.
- Internal application returns HTTP 200 from the runner.
- Internal application cannot be reached from the external workstation.
- Public application returns HTTP 200 from the external workstation.
- Both Kubernetes API endpoints remain private.

## 9. Cleanup

Do not delete the controllers, worker nodes, or controller IAM
permissions before removing the application Ingress resources.

From the runner:

```bash
kubectl --context lab-internal -n default delete ingress internal-demo
kubectl --context lab-public -n default delete ingress public-demo
```

Wait for AWS to finish deleting the ALBs and their controller-managed
resources. Confirm deletion using the AWS console or AWS CLI.

Then, from the local project directory:

```powershell
terraform plan -destroy "-out=cleanup.tfplan"
```

Review the plan before applying it:

```powershell
terraform apply "cleanup.tfplan"
```

After completion:

- Verify that no lab ALBs, target groups, worker instances, runner
  instance, NAT Gateway, Elastic IP, or lab storage remain.
- Remove the old self-hosted runner registration from GitHub.
- Retain code, documentation, evidence, and Terraform state records.
- Update the README to state that the live environment was removed.

Billing displays may take time to reflect resource deletion.
